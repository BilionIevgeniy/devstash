## Germany: tax and legal

Decide these before Stripe goes to live mode. Researched only briefly on 2026-11-06, from secondary sources: check them with a tax adviser or a lawyer.

- **VAT.** Not decided. First question: the small-business scheme (§ 19 UStG) or regular VAT. Then: the One-Stop Shop for consumers in other EU countries (above €10,000 of cross-border sales a year), reverse charge for EU businesses (net invoice with both VAT ids), and whether to use Stripe Tax (`automatic_tax` on the Checkout session, and tax ids collected in Checkout). The thresholds of § 19 and how it combines with the OSS were not confirmed.
- **Cancellation button (§ 312k BGB).** A subscription sold online to consumers needs an always available, readable button labelled "Verträge hier kündigen", leading to a confirmation page where the consumer cancels directly. The Stripe portal behind "Manage Billing" is probably not enough on its own. Without it, the consumer may cancel at any time without notice, and warning letters are possible.
- **Cancelling after failed payments.** The plan cancels the subscription after 8 tries in 2 weeks (`docs/stripe-integration-plan.md`, "`past_due` keeps Pro"). Ask whether two weeks of arrears supports ending the contract, and whether the terms must say so. If the answer is to use `unpaid`, `paymentIssue` and Manage Billing must also show for non-Pro users.
- **Other consumer rules, not researched yet.** The right of withdrawal for digital services (§ 356 BGB), the order button wording (§ 312j BGB), terms, privacy policy and imprint. The footer links for Privacy and Terms lead nowhere today.
- **Payment methods.** Cards only is the simple start. SEPA Direct Debit and PayPal are common in Germany, but SEPA settles late and can be reversed, so test the status flow before turning them on.

## Auth

- **Password length limit counts characters, but bcrypt reads bytes.** `MAX_PASSWORD_LENGTH` (72, in `auth/domain/password-reset.ts`) is applied by `.max(72)` in `auth/schemas.ts`, which counts characters. bcryptjs silently ignores everything after the first 72 bytes, so a multi-byte password such as `"é".repeat(72)` (72 characters, 144 bytes) is accepted, and a different password with the same first 72 bytes verifies against its hash. Found on 2026-10-28 while writing the schema tests; checked against the installed bcryptjs, no code changed. Fix idea: reject a password over 72 bytes (a byte-length check in the schemas, with the message saying bytes or characters accordingly) and cover it with tests. It needs its own change.
- **Old GitHub tokens in `Account` may still be live.** New rows store none since the usual OAuth flow (2026-11-06), but older rows keep theirs in plaintext, and nothing revokes them any more, so a database leak could expose any token whose revoke once failed. Fix: a data migration sets `access_token`, `refresh_token` and `id_token` to null, and the same commit removes the loop in `deleteVerifiedUserRows`, `getGitHubAccessTokens` with its test, and `github-grant.ts` with its test.
- **A stronger confirmation for deleting GitHub-only accounts.** The delete check proves a sign-in in this browser from the last 10 minutes, and a GitHub sign-in can now finish with no screen, so it no longer proves that the user saw GitHub. Idea: an email link.

## Security

- **A script and style Content-Security-Policy.** Since the audit hardening (2026-10-31) `next.config.ts` sends a CSP that covers only `frame-ancestors`, `object-src` and `base-uri`. A full policy needs per-request nonces (set in `src/proxy.ts`, which then has to run on every page, not only the authenticated ones), `script-src`/`style-src`/`worker-src`/`font-src` for Monaco (served from the app's own origin under `/monaco/`), `img-src` and `connect-src` for the R2 endpoint (the gallery and the browser's PUT) and `img-src` for GitHub avatars. Do not add `form-action 'self'` without testing: Chrome applies it to the redirect after a form post, which would break the GitHub sign-in (a Server Action redirecting to github.com). Start in `Content-Security-Policy-Report-Only`.
- **Remove uploads no item points to.** Signing is rate limited (`PRESIGN_BY_USER`), but an upload never attached to an item stays in R2 until the account is purged ("Unclaimed uploads" in `docs/architecture.md`). Fix idea: upload under a staging prefix with an R2 lifecycle rule that expires it after a day, and move or copy it to its final key in the create; or a scheduled sweep of keys no item holds.
- **`dompurify` in the audit.** `npm audit --omit=dev` reports `dompurify` (critical) through `monaco-editor`. Since 2026-11-04 the app serves Monaco itself, so this code runs in production: 0.57.0, the latest stable release on that date, pins and bundles `dompurify` 3.4.15, and `npm audit fix` cannot change a bundled copy. Upgrade `monaco-editor` when a release carries a fixed version: change the exact version in `package.json`; the copy script and the path follow it.
- **`GET /api/search` has no rate limit and ignores an abort.** The palette reads the index on app load and on every open, and an aborted read keeps running on the server. Found in the audit review of 2026-11-04. Fix idea: a per-user limit, and pass the request's signal down or skip a read while one runs.

## Items

- **Item cards are buttons, not links.** Since the intercepting routes (2026-10-30) every item on a type page has a URL (`/items/<type>/<id>`), but `ItemDrawerTrigger` is a `div role="button"` that calls `router.push`, so Cmd/Ctrl+click, "Open in new tab" and "Copy link" do not work and the route is not prefetched. Fix idea: on a type page render the card as a `next/link` `<Link>` to the item URL (an `<a>` may wrap the `<article>`); keep the button on the dashboard, whose drawer has no URL. Check that Link's soft navigation still hits the intercepted route and that the optimistic hiding of a deleted card keeps working.
- **The card's hover colour turns off over the copy button.** Since the card quick copy (2026-10-31), the copy button of `ItemCard` and `ItemRow` sits beside the `role="button"` trigger, not inside it (`ItemDrawerTrigger` `action` slot). Hovering the button leaves the card, so its `hover:bg-accent/50` turns off and the card flickers as the pointer moves onto the icon. It's cosmetic. Fix idea: add `group` to the wrapper `div` in `ItemDrawerTrigger` when an `action` is set, and switch `hover:bg-accent/50` to `group-hover:bg-accent/50` in `ItemCard` and `ItemRow`. Check that `FileRow`, which uses the trigger without `action`, keeps its own hover.
- **Focus does not return to the card after the route drawer closes.** The sheet of `ItemDrawerProvider` got its focus return on 2026-11-05 (`useItemSheet`: the opener, or a sentinel before the page when the opener is gone). `ItemRouteDrawer` on the type pages still lands on `body`: its `onCloseAutoFocus` calls `router.back()` and also fires on browser Back, and the opener would have to come through the provider of the `items/[type]` layout. Also, the sentinel puts the focus at the top of the list, not on the neighbouring row, after a delete or an unpin from the drawer. Fix idea: keep the opener in the layout's provider and focus it after `router.back()` when the list is back.
- **A signed-out delete shows a false error.** The bare `catch` of `deleteWithToast` in `ItemDrawerProvider` and the one in `ItemDetailPage` also catch the redirect of an expired session, so the user sees "Couldn't delete the item." on the way to sign-in. Older than the locked items. Fix idea: `unstable_rethrow(error)` first in each `catch`, as `DeleteCollectionDialog` does.
- **Read-only over the Free limit.** After a cancelled subscription a user with more than 50 items keeps editing them, and rewriting an old item gets around the limit. Proposed 2026-11-06, not decided: above the limit, viewing, copying, search and delete stay and `updateUserItem` refuses text items, with Edit disabled and a link to `/upgrade`. At 50 or fewer nothing changes, and favorite, pin and collections stay open. Needs a plan review.

## Collections

- **Ranking a collection's types reads every link.** `collections/queries.ts` `fetchCollections` selects each collection's `ItemCollection` rows with the item's `typeId` to rank its types, and the dashboard renders it three times (two sidebar reads and the recent collections); `/collections` reads it for each of the 21 collections of a page. Pagination bounds the collections, not their links: fine at today's sizes, but with large collections it reads one row per item. Fix idea: count `(collectionId, typeId)` in the database. That needs raw SQL or a denormalized count, and either a read of `Item` from `collections` (a foreign model, so a query in `items` that collections calls) or a column of its own: an architecture decision of its own. Left out of the collections pages and of their pagination (2026-11-04) for that reason.

## Search

- **The palette searches only the 1000 most recently edited items.** `SEARCH_INDEX_ITEM_LIMIT` in `items/queries.ts` bounds the index, because the whole index goes to the browser and is read again on every open. A Pro user past the limit does not find their oldest items, with nothing on screen to say so. Fix idea: past the limit, search on the server (a Postgres full-text index behind `GET /api/search?q=`), keeping the client index for smaller accounts.

## Database

- **Measure production latency before changing the pool.** Found in the audit of 2026-11-04: the slow pages in `next dev` come from the distance to the database (about 770 ms per new connection, 125 ms per query, from a developer's machine), and `lib/prisma.ts` keeps connections longer only in development. Production runs in `iad1` against `us-east-2` and has not been measured. Measure first, then consider Vercel's `attachDatabasePool` (check its docs), a `connectionTimeoutMillis` (pg has no default), and the `relationJoins` preview feature, since a nested select costs 4 SQL statements. Do not raise `idleTimeoutMillis` on Vercel without that: a suspended instance stops the pool's timers.
- **Reading full content for lists.** `cardItemSelect` reads each item's `content` (up to 100,000 characters) for `canCopy` and the palette's preview. Revisit when `/api/search` responses grow in bytes or time, not by item count. Fix idea: a stored preview column.
- **Drop the superseded columns (contract step).** The file upload feature (2026-10-30) added `Subscription` and `Item.fileKey` without dropping what they replace, because a push to main migrates production while the previous deployment still serves traffic, and Prisma selects every scalar column by name: dropping them in the same deploy breaks that deployment (the NextAuth adapter reads `User` without a `select`) and any Instant Rollback to it. Left: `User.isPro`, `User.stripeCustomerId`, `User.stripeSubscriptionId`, `Item.fileUrl`, all read by nothing and without data. Once the deploy with the file upload is live and no rollback before it is wanted, remove them from `schema.prisma` and create the migration with `prisma migrate dev` (it warns about the dropped columns and needs an interactive terminal).

## UI review

Left from the live review of the homepage and dashboard (2026-11-05); the three worst findings are fixed. Sizes were measured in Chromium at 375, 768 and 1280px. Not reviewed: the sign-in page, the drawer at 768px, the collapsed sidebar, light mode, other browsers, `/collections`, `/items` and the settings.

- **Last feature: a full Playwright pass over the app.** When everything else is built, go through every flow with Playwright (homepage, register, verify email, sign in, reset password, dashboard, items of each type with create, edit, delete, favorite, pin, the drawers and the full item page, collections, search palette, file and image uploads, AI features, billing and upgrade, settings, delete account) at 375, 768 and 1280px, in dark and light mode, and check each screen against the UI/UX rules in `context/coding-standards.md` (pending states, toasts, no layout shift, focus and Esc, plain errors) and common best practice (touch targets, contrast, keyboard access). It also covers what the 2026-11-05 review skipped (listed above). Findings go into this section; the ones already listed here are checked again.
- **Touch targets are under 44px on phones.** Do this one first: Edit and Delete in the drawer's action bar are 4px apart, and Delete is destructive. Top bar buttons 32px, sidebar links 32px and section headers 28px, collection card actions 28px, row favorite and copy 36px, drawer actions 38×32, drawer Close and Copy code 28px, footer links 18px, the nav's Get Started 36px. Fix idea: `max-md:min-h-11 max-md:min-w-11`, or a larger hit area through an `after:-inset-2` pseudo-element, and more space between Edit and Delete.
- **Item row titles truncate hard at 375px.** The title gets about 88px ("Settings fr…"), because the date and the two buttons take the row. Fix idea in `ItemRow`: below `sm`, move the date to the description or tag line and use `line-clamp-2` for the title. The skeleton's `h-26` follows the change.
- **The top bar is squeezed at 768px with the sidebar open.** The search button is 80px and its placeholder shows only ":"; the sidebar takes 256px of 768px. Fix idea: icon-only search below `lg` and no "New collection" label below `xl`, or the sidebar collapsed by default below `lg`.
- **Stats cards wrap and shift.** "Favorite Collections" takes two lines at 375px and at 1024px with the sidebar open, which makes the row 110px against the 88px of the `h-22` skeleton; real cards are 90px even without the wrap, so the page moves on load. Fix idea: a shorter label or `lg:grid-cols-2 xl:grid-cols-4`, `min-w-0` on the label block, a 90px skeleton.
- **The sheet overlay barely dims the page.** `bg-black/10` in `components/ui/sheet.tsx`; the separation comes from the 4px blur, and a browser without `backdrop-filter` gets almost nothing. Fix idea: `bg-black/40` or darker. The file is a shadcn primitive shared by every sheet.
- **The homepage footer is mostly dead text.** Seven of nine entries (Changelog, Documentation, API, Blog, About, Privacy, Terms) look like links and lead nowhere, and a product with sign-up has no Privacy or Terms. Fix idea: add Privacy and Terms first, hide the rest until their pages exist.
- **The homepage has no social proof.** No testimonials, user counts or logos. Fix idea: a strip under the hero, with real numbers only; until there are some, "Free forever · 50 items · no card".
- **An email link for another account.** Signed in as A, a user who finishes a password reset or an email verification for B sees "You can now sign in", and `/sign-in` then sends them to A's dashboard. Rare. Fix idea: a page that says the action is done and offers to switch accounts.
- **The homepage calls to action ignore the session.** The header knows the session (`useHasSession`), but `HeroSection`, `CTASection` and `PricingCard` still show a signed-in user links to `/register`, which sends them on to the dashboard. Fix idea: small client links built on the same hook, so the page stays static.
- **The homepage code mock is cut off at 375px.** 523px of content in 341px, scrollable with no hint. Fix idea: wrap long lines on phones or add a fade at the right edge.
- **No skip link on the homepage.** The fixed header comes before the main content in the tab order.
