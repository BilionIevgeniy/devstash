# 9. Hooks, forms and editor focus

## Why

Three small, real problems, each a textbook case for a React 19 API:

- `use-palette-hotkey.ts` has `[isOpen, onToggle]` in its effect dependencies, so the keyboard listener is removed and added again on every toggle. `use-unsaved-changes.ts` has the same pattern with `onDirtyChange`. That is what `useEffectEvent` is for.
- Forms are inconsistent: `SignInForm` and `ForgotPasswordForm` use `<form action>` with `useActionState`, while `ChangePasswordForm`, `ResetPasswordForm`, `ConfirmEmailForm` and `RegisterForm` are plain forms too but use `onSubmit` + `preventDefault` + `useTransition`. Item forms keep `onSubmit` for a reason (controlled state with Monaco).
- The Monaco editors (`features/editor/components/CodeEditor.tsx`, `MarkdownEditor.tsx`) cannot be focused from outside: the field label does nothing, and on a validation error the form cannot move focus to an invalid editor field.

Interview angle: "Why `useEffectEvent`?", "`useActionState` vs `onSubmit`: when which?", "When is an imperative handle the right tool?"

## Scope

1. **`useEffectEvent`** in `use-palette-hotkey.ts` and `use-unsaved-changes.ts`: the listener subscribes once; the latest callback is read through the effect event (`use-search-index.ts` is the example already in the repo)
2. **Forms**: move `ChangePasswordForm`, `ResetPasswordForm` and `ConfirmEmailForm` to `<form action>` + `useActionState` (+ `useFormStatus` in the submit button) like `SignInForm`; keep the user's input on error. `RegisterForm` posts to the `/api/auth/register` route with `fetch`: the plan review decides whether it moves to a Server Action or stays (and writes the reason). Write the rule in `coding-standards.md`: plain forms use `useActionState`; forms with controlled rich editors keep `onSubmit` + `useTransition`, with the reason
3. **Editor handle**: `CodeEditor` and `MarkdownEditor` take `ref` as a prop (React 19, no `forwardRef`) and expose a minimal handle with `useImperativeHandle`: `focus()` only (add more only when a real use needs it)
   - the field label focuses the editor: `Field` (`components/common`) renders the label, so the plan decides how a click reaches the handle (an `onLabelClick` prop on `Field`, or a label `htmlFor` pointing at Monaco's textarea id)
   - on a failed submit, the form focuses the first invalid field, editor included
4. Check the React Compiler handles each changed hook (no manual `useMemo`/`useCallback`, per `coding-standards.md`)

## Non-goals

Inserting AI text at the cursor or any other new editor feature, refactoring item forms to `useActionState`.

## Acceptance criteria

- The hotkey listener is added once per mount (check with a test or a breakpoint), toggling still works
- Change and reset password work without JavaScript-specific `onSubmit` code and keep input on error
- Clicking the label of a code/markdown field focuses Monaco; a failed submit focuses the first invalid field
- `npm run lint` passes with the deprecated-API rule

## Tests

RTL (feature 3): hotkey hook subscribes once; password form shows the error and keeps input; label click calls the handle's `focus`.
