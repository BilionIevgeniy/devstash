# 8. Server search with debounce

## Why

- The command palette loads a search index when the app loads and on refresh: `GET /api/search` (`src/app/api/search/route.ts`) returns up to `SEARCH_INDEX_ITEM_LIMIT = 1000` items with full content (`features/items/queries.ts`) plus the user's collections (`getSearchableCollections`), and the browser searches it with Fuse.js (`features/search/_internal/components/fuzzy-search.ts`). A Pro user has no item limit, so **item 1001 can never be found**, and the payload grows with every item. The route has no rate limit.
- Interview angle: "Debounce vs `useDeferredValue`: what does each solve?", "How do you handle out-of-order responses?", "How do you build full-text search in Postgres?"

## Decisions

- **ADR required** (cross-file decision 5): ESLint bans raw SQL (`$queryRaw`, `$queryRawTyped`) in `queries.ts` and in services (ADR 0009). The full-text read belongs to the feature that owns the model: items in `items`, collections in `collections`; `search/services` composes them (`search` owns no model). The ADR decides how the owner runs it: a documented, narrow lint exception for one file (e.g. `items/_internal/search-queries.ts`), or a Prisma feature that covers it if one exists for the installed version. Do not work around the rule
- Tag names live in another table, so a GIN index on items cannot cover them. The plan decides: a generated/denormalised search column, or a second query on tags merged in the service

## Scope

1. **Database**: Postgres full-text search (`tsvector` over title, description, content) and/or `pg_trgm` for typos; a GIN index added by a migration (check the extension is available on Neon); ranking; `userId` first; page size ~20 with a cursor. Collections: search by name and description the same way
2. **Change the existing route** `GET /api/search` to `GET /api/search?q=&cursor=` (Server Actions run one at a time, so typeahead stays a route, as `coding-standards.md` says): session check, Zod-parsed params, one service call, `Cache-Control: private, no-store`, a rate limit through `lib/rate-limit.ts` (new limiter), and the request's abort signal passed down so a cancelled search stops on the server too
3. **Client** (`use-search-index.ts`, `PaletteResults.tsx`, `PaletteDialog.tsx`):
   - debounce the request (~250 ms) in a small hook; each request carries an `AbortController` signal and aborts the previous one, so a slow old response never overwrites a newer one (`use-search-index.ts` already uses `useEffectEvent`: keep that pattern)
   - `useDeferredValue` only for local rendering, and only if a measurement shows the input lags; write the measurement in the PR
   - an empty query shows recent items without a request
4. **Retire** the in-browser index: `fetch-search-index.ts`, `fuzzy-search.ts` (and its test), `SEARCH_INDEX_ITEM_LIMIT`, and the `fuse.js` dependency, once nothing uses them

## Non-goals

Semantic/AI search, searching inside files, highlighting inside long content.

## Acceptance criteria

- A user with 1500 items finds item 1500 by title and by a word in its content; collections are found by name
- Typing fast sends at most one request per pause; the list always matches the current input
- Search never returns another user's items or collections (feature 4 matrix)
- The palette no longer downloads all items; `fuse.js` is gone from `package.json`

## Tests

Unit: query parsing, the debounce hook with fake timers, the race (a late response is ignored). Integration (feature 4): ranking and user scope against Postgres. RTL: the palette shows results for the latest input.
