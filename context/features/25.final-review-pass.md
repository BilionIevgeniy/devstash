# 25. Final review pass

## Why

- The UI was reviewed live once (2026-11-05), and only in part: the sign-in page, the drawer at 768px, the collapsed sidebar, light mode, other browsers, `/collections`, `/items` and the settings were never looked at.
- The unit tests have mostly never been shown to fail: all passed on their first run. Only the component and hook tests were checked by breaking the code (feature 3, 31 breaks, all caught).
- Interview angle: "How do you know your tests test something?", "How do you review a whole product before a release?"

## Prerequisite

Every other planned feature merged.

## Scope

1. **A full Playwright pass over the app** (Playwright MCP or the `ui-reviewer` agent with the demo password, the dev server started by the user): homepage, register, verify email, sign in, reset password, dashboard, items of each type (system and custom) with create, edit, delete, favorite, pin, the drawers and the full item page, collections, search palette, file and image uploads, AI features with their marking, billing, upgrade, the cancellation flow, the AGB, the consent banner, settings, delete account; at 375, 768 and 1280px, dark and light mode, signed in and signed out. Each screen against the UI/UX rules in `context/coding-standards.md` (pending states, toasts, no layout shift, focus and Esc, plain errors) and common practice (touch targets, contrast, keyboard access)
2. **Findings are fixed in this feature** (the rule "Found work" in `context/ai-interaction.md`); only what needs a release or a professional goes to `context/todo-before-live.md`
3. **Mutation check of the unit tests**: break one rule at a time in the source (for example `>` to `>=` in `isUnclaimedUploadDue` of `files/domain/file-rules.ts`, remove the `Math.max(1, …)` clamp in `lib/http/retry-after.ts`, remove `.toLowerCase()` from `emailSchema`), confirm the matching test goes red, revert. A rule whose break stays green gets its test. Record the breaks and the result in the PR
4. Run `/cleanup` and the `code-reviewer` over all of `src/` once
5. **The colour threshold of the screenshots** (found after feature 23, PR 56): `toHaveScreenshot` keeps Playwright's default `threshold` of 0.2, which did not see a whole row of the palette turn from `--popover` to `--muted` in the dark theme, so a baseline without a selection passed for months. Fix idea: a lower `threshold` in `playwright.config.ts` (0.05 to start with), the baselines taken anew from the e2e job and looked at, and `--repeat-each` to see that nothing flickers

## Non-goals

New features, a redesign, a mutation-testing tool in CI (a one-time manual check).

## Acceptance criteria

- Every screen in the list checked at three widths, both themes, signed in and out; every finding fixed or, if it needs a release or a professional, in `todo-before-live.md`
- Every rule broken in the mutation check is caught by a test

## Docs to update

`context/coding-standards.md` if a rule changed, `context/feature-history.md`.

## Model

- Plan: sonnet (no new decision)
- Implementation: sonnet; the fixes follow the row of what they change
- architecture-reviewer: opus
