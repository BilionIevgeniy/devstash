# 18. Custom item types

## Why

- The homepage sells "Custom item types" under Pro, marked "(coming soon)" since 2026-11-11 (`PricingSection`, the plan table in `context/project-overview.md`). A real product does not sell what does not exist.
- The second half of the contract step of feature 17: the superseded columns are dropped once the `@ignore` deploy is live.
- Interview angle: "How do you let users extend a fixed data model safely?", "How do you keep URLs stable when names change?"

## Prerequisite

Feature 17 merged and live, and no Instant Rollback to a deployment before 17 wanted: the drop breaks every deployment whose client still selects the columns.

## Scope

1. **First commit, its own migration: drop the superseded columns** `User.isPro`, `User.stripeCustomerId`, `User.stripeSubscriptionId`, `Item.fileUrl` (`@ignore`d by 17). `prisma migrate dev` warns about the dropped columns and needs an interactive terminal
2. **The model**: `ItemType` already has `userId`, `isSystem`, `icon`, `color` (`prisma/schema.prisma`). Add what the URLs need: a stable slug, unique per user (`@@unique([userId, slug])`) and never equal to a system type's name, expand-only. `item-types` owns the model and its services
3. **CRUD** for Pro users in the settings or a types page (the plan decides; the sidebar shows them below the system types), gated by `getEntitlements` (`billing/queries.ts`), never the session
   - **Colour and icon**: a fixed palette of theme colours (`@theme` tokens in `globals.css`) and the icon set of the system types; no free hex value, since "No inline styles" (`coding-standards.md`) rules out a `style` colour
   - **Rename**: changes the name, never the slug, so bookmarked item URLs keep working
   - **Delete**: a type with items is refused with a plain message (the user moves or deletes its items first); `Item.typeId` is required
   - **Content shape**: a custom type is a text type (content and language like a snippet or a note); file and URL behaviour stay with the system types. The plan confirms this
4. **Lookups by name add the owner** ("System types are shared" in `docs/architecture.md`, Known risks): `getItemTypeByName` looks among the system types only; a lookup of a custom type takes the user, or a user could create items of another user's type
5. **Everywhere a type appears**: the sidebar and its counts, the type pages `/items/<slug>`, the create and edit forms (`ItemTypeSelect`), the dashboard, `/pinned` (`getPinnedFirstPages` in `items/queries/lists.ts` reads one first page per type, seven reads today; with custom types it reads the first rows of every type in one query), the palette and search by type, the collection type ranking, JSON export and import (ADR 0019, ADR 0020: the types travel with the items, an import creates missing types of the importer), the delete-account purge
6. **Remove "(coming soon)"** from the homepage pricing (both languages) and from the plan table in `context/project-overview.md`
7. **What a downgrade does to custom types** is decided in feature 19 (downgrade rules); until then a former Pro user keeps them as they are

## Non-goals

Custom fields per type, sharing types between users, file-backed custom types, the downgrade rules (feature 19).

## Acceptance criteria

- The columns are dropped and the live deployment kept working through the deploy
- A Pro user creates, renames and deletes a type; its items have stable URLs; a Free user cannot create one (refused by the service, not only hidden)
- Every list, search, export and import handles custom types; `/pinned` reads its first pages in one query
- "(coming soon)" is gone

## Tests

- Unit: the slug rule and its collision with system names, the delete refusal, the schema
- Integration, a cross-user case for each new query and service: A cannot read, rename, delete or create items of B's type; a lookup by name never returns B's type; the export of A carries only A's types
- E2E: a Pro user creates a type and an item of it, opens it by URL, renames the type, the URL still works
