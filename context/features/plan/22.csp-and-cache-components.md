# 22. CSP and Cache Components

## Why

- **The CSP is partial.** Since the audit hardening (2026-10-31) `next.config.ts` sends a policy that covers only `frame-ancestors`, `object-src` and `base-uri`. Nothing limits where the page may connect, load images or start workers.
- **The two belong together.** A nonce-based CSP needs a nonce per request, which makes every page dynamic; the installed Next docs say Partial Prerendering does not work with it. Cache Components makes the static shells this feature wants. So the CSP is chosen to work with static pages, and lands first.
- **Nothing is cached today.** `src/app/(app)/layout.tsx` sets `export const dynamic = "force-dynamic"` (redundant: the session cookie already makes the routes dynamic), and every mutation calls `refresh()`. Consistent, but never decided in an ADR. Next.js 16.4 recommends Cache Components (with Partial Prefetching) for every app and announces it as the default in Next.js 17; `force-dynamic` is not allowed with it.
- Interview angle: "What does your CSP protect, and what not?", "What is cached in your app and why?", "`updateTag` vs `revalidateTag` vs `refresh`", "What is a static shell?"

## Prerequisite

Feature 21 green: this change touches the headers and every route.

## Scope

### A. CSP and leak-proofing (first)

1. **ADR "Content-Security-Policy"**, honest about what it does: App Router puts inline flight scripts (`self.__next_f.push`) on every page, and `experimental.sri` adds integrity attributes to external chunks only (and its support under Turbopack, the build default, is not verified). So the static-compatible policy is `script-src 'self' 'unsafe-inline'`, and its value lies elsewhere: `connect-src`, `img-src`, `worker-src`, `font-src`, `object-src`, `base-uri`, `frame-ancestors`, limiting where data can go, not blocking injected scripts. Nonces are rejected because they make every page dynamic
2. **The policy**: `script-src`/`style-src`/`worker-src`/`font-src` for Monaco (served from the app's own origin under `/monaco/`), `img-src` and `connect-src` for the R2 endpoint (the gallery and the browser's PUT) and the Sentry ingest (`https://*.ingest.de.sentry.io`, or the browser SDK stops reporting), `img-src` for GitHub avatars, `connect-src 'self'` for the metrics route of feature 20. Do not add `form-action 'self'` without testing: Chrome applies it to the redirect after a form post, which would break the GitHub sign-in (a Server Action redirecting to github.com)
3. **`Content-Security-Policy-Report-Only` first**, with a report endpoint or the browser console in the E2E run; enforced once the suite of feature 21 is green with it
4. **Next.js writes uncaught server errors to the log with their message.** `console.error(err)` in its own error handling runs for an error nobody caught, and a Prisma error quotes the arguments of the failed call, so the Vercel log can hold an email address or a title. Catch it in the page's query and log it through the logger, or a log drain or filter that drops the message of those lines (the plan decides)
5. **What leaves the app is checked automatically.** Feature 6 proved it by hand (a stand-in ingest server, a production build, a Chromium script; the method in ADR 0016). An E2E spec starts a local ingest, builds with its DSN, triggers one error per path through throw routes that exist only in the test build, and asserts the bodies (no token, email or title; one event per error; no request from an idle page). It also proves that `connect-src` does not block Sentry

### B. Cache Components

6. **ADR "Caching strategy"** first: what is cached (system item types, entitlements per user with a tag, the marketing page, the legal pages), what stays per request (everything else), and the invalidation matrix per Server Action. It names custom types (feature 18: per-user types are cached per user or not at all), the entitlements written by the webhook and the reconciliation (feature 19: `revalidateTag`), and consent as client state that is never cached (feature 20)
7. Enable `cacheComponents` and `partialPrefetching` in `next.config.ts` (names and behaviour checked in the installed docs); remove `force-dynamic`
8. Fix what the build reports: dynamic reads (`cookies()`, the session) inside `<Suspense>` so routes get a static shell plus streamed per-user parts
9. `'use cache'` with `cacheLife` and `cacheTag` on the chosen reads; per-user data takes `userId` (and the locale) as arguments so cache keys separate users; no `'use cache'` function calls `getSessionUser`, `auth()` or `cookies()`
10. Invalidation: `updateTag` in Server Actions where the user must see their own change at once, `revalidateTag` where eventual is fine, `refresh()` where no cached data changed. `updateTag` works only in Server Actions: the Stripe webhook and the cron (Route Handlers) use `revalidateTag`. Each in the ADR's matrix
11. `export const ensureStatic = "navigation"` on the marketing pages (`/`, `/de`) and the legal pages
12. **`<Activity>`**: Next keeps recently visited routes hidden but mounted; check `useUnsavedChanges`, dialogs and effects (React docs: effects are cleaned up while hidden)
13. `next upgrade --agent` or the migration guide as a checklist, not an autopilot
14. **Screenshots**: Cache Components may change loading states and so the baselines of feature 21. A baseline is updated only after reviewing its diff, never by a blind `--update-snapshots`

### C. Measurements

15. **Before and after**: TTFB and LCP on the dashboard, database queries per page, in `docs/performance.md`, lab numbers
16. **Production database latency.** The audit of 2026-11-04 found the slow pages in `next dev` come from the distance to the database (about 770 ms per new connection, 125 ms per query, from a developer's machine); `lib/prisma.ts` keeps connections longer only in development. Production runs in `iad1` against `us-east-2` and has not been measured. Measure it; a pool change (Vercel's `attachDatabasePool`, `connectionTimeoutMillis`, the `relationJoins` preview feature, since a nested select costs 4 SQL statements) is decided in the ADR from the numbers, in scope only if they show a problem. Do not raise `idleTimeoutMillis` on Vercel: a suspended instance stops the pool's timers
17. **Endless lists at 500 rows.** Feature 12 left out `@tanstack/react-virtual` until a profile shows a problem. Run the React profiler once on `/favorites` with 500 favorites (17 pages loaded); virtualize only if it shows one

## Non-goals

A remote cache handler (Redis), caching AI responses, caching file URLs, nonces, a CSP report service.

## Acceptance criteria

- The CSP is enforced, the suite of feature 21 and the egress spec are green with it, and the static pages are still `○`
- `next build` passes with Cache Components on; the build output shows which routes have a static shell
- A user never sees another user's cached data (the integration matrix plus an E2E with two users)
- After every mutation the user sees the change (feature 21 green)
- Before and after numbers, the production latency and the 500-row profile documented

## Tests

The full E2E suite, the egress spec, the integration matrix, a test that two users get different cached entitlements.
