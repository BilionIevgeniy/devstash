# 4. Tenant isolation integration tests

## Why

- The first quality goal (`docs/arc42-lite.md`) is that a user can never read or change another user's data. Today that is checked by code review and by service tests that **mock Prisma** (13 test files), so a `where` without `userId` passes every test.
- Interview angle: "How do you prove user A cannot read user B's item?", "Unit vs integration test: when is a mock not enough?"

## Scope

1. **The test database contract** (used again by features 5 and 15; cross-file decision 2 in `README.md`):
   - `TEST_DATABASE_URL`: a Postgres service container in GitHub Actions, locally Docker Postgres or a Neon branch that is neither `development` nor `production`; `prisma migrate deploy` before the run
   - a new guard `requireTestDatabase` next to `requireDevDatabase` in `scripts/require-dev-database.ts` (allows `localhost` or the configured test host only). `requireDevDatabase` is **not** reused: it allows only the development host
   - a test seed (`scripts/seed-test.ts`, guarded by `requireTestDatabase`) that creates a Free user and a Pro user with a `Subscription` row (the normal seed creates the Pro user only on the development database)
   - mocked in integration tests: `@/lib/rate-limit`, `@/lib/r2`, `@/lib/email`, `@/lib/stripe`, `@/lib/openai`. Only Prisma is real
2. **Vitest project `integration`**: `*.int.test.ts`, node environment, `fileParallelism: false` (one shared database; truncating between files must not race), run with `npm run test:integration`; not part of the default `npm run test` (it needs a database), but a separate CI job on every PR. The CI job lists its env vars (only the test database is real)
3. **Fixtures**: two users (A and B), each with items, collections, tags and a favorite; created through the services, truncated between test files
4. **The ownership matrix**: for every read in `features/*/queries.ts` and every write in `features/*/services/`, user A asking for user B's id gets nothing or a "not found" result, and B's rows are unchanged. Include the raw-SQL toggles in `items/services/item.ts` and the advisory-lock path in `create-item.ts`
5. **Free limit race**: two parallel creates at 49 items end with exactly 50 (proves the advisory lock)
6. Note any query without `userId` that the matrix finds (expected: `item-types` `getItemTypeByName` and `getItemTypesById`; the second has no filter at all, not even `isSystem`) and either scope it or document why it is safe in `docs/architecture.md` "Known risks"

## Non-goals

Load tests, E2E (feature 5), testing Stripe or R2 against real vendors.

## Acceptance criteria

- `npm run test:integration` runs against a fresh database and is green; CI runs it on every PR
- Every exported query and service that takes a `userId` has at least one cross-user case
- Removing `userId` from any covered `where` makes a test fail (check one)
