# 15. AI output marking

## Why

- **Deadline 2026-12-02.** AI Act Art. 50 (2): the provider of an AI system that generates text marks the output in a machine-readable, detectable way. ADR 0014 records that DevStash is public, anyone can register, and DevStash is the provider. The AI features existed before 2026-08-02, so the transition ends on 2026-12-02, whether or not anyone pays.
- **Decision, without a lawyer: mark it.** The exception for "assistive functions for standard editing" is doubtful for generated summaries, explanations and optimized prompts; tags are arguable, and marking them too keeps one rule. Marking is cheap, and it removes the dependency on facts ADR 0014 calls unconfirmed. A lawyer's check stays in `context/todo-before-live.md`.
- A visible label alone does not meet Art. 50 (2), which asks for machine-readable marking. The visible label is an extra for the reader.
- Interview angle: "How do you make generated content traceable?", "What does a regulation mean for a data model?"

## Scope

1. **ADR 0014 addendum first** (a new record that amends 0014, since an accepted record is not edited): what is marked, the technique, what an edit does, and that watermarking short text is not technically feasible, which Art. 50 (2) allows for ("as far as technically feasible"). Before writing it, check whether the Commission's final code of practice on marking and labelling is published and follow it where it applies.
2. **What is generated and where it is saved** (check against `src/features/ai`): the summary saved as the item's description (`AiDescriptionSummary`), the accepted tags (`AiTagSuggestions`), the optimized prompt saved as the content (`AiPromptOptimizer`). The code explanation (`AiCodeExplanation`) is not saved: it is marked only in the markup.
3. **A stored flag per field**: a migration adds the marking to `Item` (for example `aiGeneratedFields` or one boolean per field, and for tags a flag on `ItemTag`; the plan decides the shape). Expand-only and backward compatible with the live deployment (`coding-standards.md`, "Database").
4. **What an edit does**: the flag stays until the user edits that field; an edit of the field clears it (the text is then the user's). The rule is a pure function in `items/domain/` with its test.
5. **Machine-readable in the markup**: a `data-ai-generated` attribute (name decided in the ADR) on the element that shows a marked field, in the drawer, the item page and the card's description, and on the explanation.
6. **Visible label**: a small "AI-generated" hint next to a marked field, translated (`en/` and `de/`).
7. **Export and import**: the JSON export carries the flag per field, the import reads it (ADR 0019, ADR 0020: the format is versioned; an old file without the field imports as not marked). The future public API carries it the same way.
8. **One E2E journey** in this feature: a Pro user accepts a summary, sees the label and the attribute, edits the description, and the label is gone. The AI route is mocked with a fixed fake.

## Non-goals

Watermarking text, marking the AI's input, a consent or disclosure dialog before an AI call (Art. 50 (1) is about systems that interact with people as such: the AI buttons say what they do).

## Acceptance criteria

- The ADR addendum is accepted before 2026-12-02 and the feature is merged before that date
- Every saved AI output carries the flag; an edit of that field clears it; export and import keep it
- The markup carries the attribute wherever a marked field is shown, and the label is visible

## Tests

- Unit: the edit rule in `items/domain`, the export and import schema with and without the flag
- Integration: a cross-user case for the write of the flag (B's call sets it, A's call with B's id changes nothing)
- E2E: the journey of scope item 8
