# 7. URL filters and sort

## Why

- `/items/[type]` has pagination but **no sort and no tag filter**. Tags exist on items, but nothing can be filtered by them.
- The sorts on `/favorites` (one for items, one for collections) and on `/pinned` (one per type group) live in `useState` behind `SortSelect` (`app/(app)/_components/SortSelect.tsx`), so they are lost on reload and cannot be shared as a link.
- Interview angle: "Where do you keep filter state and why?", "What does `useTransition` do for a filter?", "How do you avoid showing stale results?"

## The URL contract (cross-file decision 3 in `README.md`)

- Sort values are the existing `FAVORITE_ITEM_SORTS` = `newest | oldest | a-z | z-a | type` from `features/items/domain/favorite-sort.ts`, and their subsets where a list already uses one. Their meaning stays as it is (on favorites, "newest" means newest favorited)
- `/items/[type]`: `?sort=&tag=&page=` (no `type` parameter: the type is in the path). Changing sort or tag resets `page` to 1
- `/favorites`: `?itemSort=&collectionSort=` (two independent lists). **No `page`**: feature 12 makes this list cursor-based
- `/pinned`: the plan review decides between one `?sort=` for all type groups and keeping the per-group sort local; record the choice. **No `page`**
- `/collections/[id]` shows its newest items grouped by type; it is **left out** of this feature (a title sort would fight the grouping). Note it in `docs/architecture.md`
- Unknown or invalid values fall back to the defaults, never throw

## Scope

1. A pure parser per page (the feature's `domain/` with Zod in `schemas.ts`, or `lib/` if shared; the plan review decides by the architecture rules) with its tests
2. **Server side**: the page reads `searchParams` (async in Next 16), passes the parsed values to the feature query; sorting and the tag filter happen in the database with `userId` first. Where a list is sorted in memory today (`favorite-sort.ts`), the plan review decides whether the sort moves into the query
3. **Client side**: `SortSelect` and a new tag filter write the URL with `router.replace` inside `startTransition` (a non-urgent update: the current list stays visible, dimmed with `isPending`, until the new one arrives; Back does not step through every click)
4. **Suspense**: the list sits in `<Suspense key={…params}>` with its skeleton; the header, filters and `PaginationNav` stay **outside** the boundary so they do not flash or lose focus (fixes the issue recorded in `feature-history.md`)
5. Empty result: "No items match these filters" with a "Clear filters" link

## Non-goals

Free-text search (feature 8), saved filters, more than one tag at a time, `/collections/[id]`.

## Acceptance criteria

- Reload and a copied link keep sort, filter and page on `/items/[type]` and the sorts on `/favorites` (and `/pinned` per the decision)
- Changing a filter shows the old list dimmed, then the new one; the filter control keeps focus
- Invalid params (`?sort=foo&page=-3`) render the default view
- Queries never return another user's items (feature 4 matrix extended)

## Tests

Unit tests for each parser (defaults, invalid values, page reset). RTL (feature 3): changing the select calls `router.replace` with the right URL. E2E: filter, reload, same result.
