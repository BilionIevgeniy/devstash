# 12. Client data and infinite lists

## Why

- Two hooks are hand-written fetch state machines with their own loading, error and abort logic and **no cache**: `features/items/_internal/components/hooks/use-item-sheet.ts` (refetches the item detail on every drawer open) and `use-collection-options.ts` (refetches on every form mount). (Search is handled by feature 8 and not touched here.)
- `/favorites` and `/pinned` load **every** favorite or pinned item with no limit (`getFavoriteItems`, `getAllPinnedItems` in `features/items/queries.ts`) and render them all.
- Interview angle: "Server state vs client state", "When do you add TanStack Query to an App Router app, and when not?", "Cursor vs offset pagination", "Two caches: how do you keep them consistent?"

## Decisions

- **The plan review decides first whether TanStack Query is needed at all.** The product problem is the unbounded queries; cursor pagination solves it alone. Query is added only if it clearly removes hand-written fetch code and the plan names that code. If added: **only for data the client fetches itself** (the two hooks above and the infinite lists). Pages keep reading data in Server Components; Server Actions stay the way to change data. The cost is a second cache: every Server Action that changes these resources must also invalidate the matching query keys. Record this in an ADR
- **Infinite scroll only on `/favorites` and `/pinned`.** Type and collection pages keep numbered pagination (shareable, accessible, works with the URL filters of feature 7)
- **Virtualization only if measured**: a card grid of a few hundred items is fine; add `@tanstack/react-virtual` only if a profile shows a problem. If added, it lives in its own small component (the React Compiler skips it)

## Scope

1. `@tanstack/react-query` (pinned), one `QueryClient` per browser session in a client provider in the app layout; Devtools in development only
2. Query key factory per feature (e.g. `itemKeys.detail(id)`), in the feature's `components/` role
3. Replace the two hooks with `useQuery`; keep their public return shape where possible so components barely change; abort comes from the `signal` Query passes in
4. Invalidation: the actions that change an item, its favorite/pin state or collections trigger `queryClient.invalidateQueries` for the affected keys (a small helper used by the client hooks that call those actions)
5. **Cursor pagination** in the favorites and pinned queries. The cursor encodes the **sort key plus `id`** (`id` alone is wrong when the list is sorted by title or type; the sorts come from feature 7), `take` + 1 to know if there is more; a Route Handler for the next page (parallel reads, per `coding-standards.md`). `/pinned` is grouped by type in accordions: the plan decides between paging per group and keeping it grouped with a limit per group
6. `useInfiniteQuery` + an `IntersectionObserver` sentinel to load the next page; a "Load more" button as the accessible fallback; the first page is rendered on the server and passed as initial data
7. Optimistic favorite/pin (`useOptimistic` today) keeps working with the cached lists

## Non-goals

Moving page data from Server Components to Query, offline support, replacing numbered pagination.

## Acceptance criteria

- Opening the same item twice in the drawer fetches once within the stale time; editing it shows the new data next time
- `/favorites` with 500 favorites renders the first page fast and loads more on scroll; Back keeps the scroll position reasonably
- No list or detail shows another user's data (feature 4 matrix extended to the new route)
- Bundle size change measured and noted in the PR

## Tests

RTL with a fresh `QueryClient` per test: loading, error, invalidation after an action. Unit: cursor helper. Integration: cursor pages are stable and scoped. E2E: scroll loads more.
