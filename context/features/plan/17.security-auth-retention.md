# 17. Security, auth and data retention

## Why

- Four known holes in auth, each small, none fixed (found in the reviews of 2026-10-28 to 2026-11-13).
- Data is kept longer than the privacy notice should allow: GDPR storage limitation applies from the first account (ADR 0014, Context), and the public deployment takes registrations today. So retention is an obligation now, not hygiene.
- The first half of the contract step for the superseded columns: the second half (the drop) is a separate deploy in feature 18.
- Interview angle: "How do you hash passwords, and what are bcrypt's limits?", "How do you avoid account enumeration?", "How do you drop a column without downtime?", "How do you run scheduled jobs on serverless?"

## Scope (commit groups)

### A. Auth hardening

1. **The password limit counts bytes.** `MAX_PASSWORD_LENGTH` (72, `auth/domain/password-reset.ts`) is applied by `.max(72)` in `auth/schemas.ts`, which counts characters, but bcryptjs ignores everything after the first 72 bytes: `"é".repeat(72)` (144 bytes) is accepted, and another password with the same first 72 bytes verifies against its hash. Reject a password over 72 bytes (a byte-length check in the schemas, the message saying what is counted), with tests including multi-byte input
2. **HMAC for the rate-limit identifiers.** `toIdentifier` in `lib/rate-limit.ts` is a plain SHA-256 of an email, an IP address or a user id, so a leaked Upstash database can be reversed by trying a list of emails or the IPv4 space. An HMAC with a server secret `RATE_LIMIT_HASH_KEY`; it resets every counter once (say so in the PR). The secret: `.env.example`, the map of `scripts/e2e-server-env.ts` (its unit test fails on a missing name), a value in every Vercel environment (the user sets it), the GitHub secret for the e2e job if the job needs it
3. **Resend verification does not tell a pending account apart during an email outage.** `resendVerificationLink` (`auth/services/email-verification.ts`) answers `emailSendFailed` only for an address with a pending registration. Log the failure and answer success, as `requestPasswordResetLink` does, at the cost of the "we couldn't send" hint
4. **A stronger confirmation for deleting a GitHub-only account.** The delete check proves a sign-in in this browser in the last 10 minutes, but a GitHub sign-in can finish with no screen, so it no longer proves the user saw GitHub. An email link to the account's address confirms the delete. Decide what happens when the GitHub account's email is not verified or not available (the delete is refused with a plain explanation, or falls back to the reauth): the plan decides and the auth review checks it
5. **An email link for another account.** Signed in as A, a user who finishes a password reset or an email verification for B sees "You can now sign in", and `/sign-in` then sends them to A's dashboard. A page that says the action is done and offers to switch accounts (sign out, then sign in as B)

### B. Schema contract, step one (expand/contract, ADR 0013)

6. **`@ignore` on the superseded columns**: `User.isPro`, `User.stripeCustomerId`, `User.stripeSubscriptionId`, `Item.fileUrl` are read by nothing and hold no data. `@ignore` removes them from the generated client with no migration (check `@ignore` against the installed Prisma 7 docs, and that the new `migrate diff` check of feature 16 stays green with it). The deployment that is live keeps selecting them by name, so they must stay in the database until this deploy is live: the drop is the first commit of feature 18
7. **Old GitHub tokens**: a data migration sets `access_token`, `refresh_token` and `id_token` of `Account` to null (new rows store none since 2026-11-06, older rows keep theirs in plaintext, and nothing revokes them any more). The same commit removes the revoke loop in `deleteVerifiedUserRows`, `getGitHubAccessTokens` with its test, and `github-grant.ts` with its test. Safe for the live deployment: null tokens only skip its revoke loop

### C. Data retention (Vercel cron)

8. **One cron dispatcher route** behind `CRON_SECRET` (`Authorization: Bearer`, compared in constant time), in `src/app/api/cron/` (path decided at the plan), declared in `vercel.json`. Check the plan's cron limit first: Hobby runs a cron at most once a day, so every job is daily and must finish within the function timeout, paging through its rows. `CRON_SECRET` in `.env.example`, the map of `scripts/e2e-server-env.ts` and every Vercel environment (the user sets it). The route is thin: it calls one service per job, each logged with counts and ids only. Feature 19 adds the Stripe reconciliation to the same dispatcher
9. **Expired tokens**: delete the expired `VerificationToken` rows of an address in the same transaction that creates a new token, and the remaining expired rows in the daily job
10. **Never-verified users**: the daily job removes a registration that was never verified after N days (N decided in the plan, stated in the privacy notice), with its rows, through the existing delete path of `account`
11. **Unclaimed uploads**: an object uploaded to R2 that never became an item (the dialog closed, the file removed, the type switched, the create failing after the upload) stays until the account is purged. A daily sweep deletes every object under `users/` older than 24 hours that no `Item.fileKey` holds. No staging prefix: `isUserKey` (`files/domain/file-rules.ts`) rejects nested keys on purpose, and the purge by prefix stays as it is
    - **Where it lives**: the sweep reads `Item.fileKey` across users, which `files` (rank 3) may not read; the service goes in `items` (it owns `Item`) and uses the list and delete of R2 objects from `files`
    - **The 24 hours** are longer than the presign lifetime plus any realistic time a create dialog stays open; and the create refuses with a plain error code when its file is gone at save (an item never points to a deleted object)
    - **Idempotent**: it lists `users/` page by page, can run twice with the same result, deletes in batches

## Non-goals

A CSP (feature 22), a retention period for active accounts, a queue or a worker other than Vercel cron.

## Acceptance criteria

- A 73-byte password is refused, a 72-byte one accepted; rate limits work with the HMAC identifiers
- Resend verification answers the same for every address during a send failure
- A GitHub-only account cannot be deleted without the emailed confirmation
- The `@ignore` deploy is live with the columns still in the database, and no `Account` row holds a token
- The cron route refuses a call without the secret; each job runs twice with the same result

## Tests

- Unit: the byte check, the HMAC identifier, the cron secret check, the retention rules (age, N days) in `domain/`
- Integration, a cross-user case for each new query and service: the sweep deletes A's unclaimed object older than 24 hours, keeps A's object that an item holds and every object of B; the purge of never-verified users leaves B's rows; the token cleanup leaves B's token (the fixture's unused token)
- E2E: the account-switch page; the auth-auditor reviews the diff
