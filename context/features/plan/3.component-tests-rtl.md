# 3. Component tests with React Testing Library

## Why

- About 90 test files exist, all in Vitest's `node` environment. They test domain rules, schemas, services and routes. **No test renders a component or runs a hook**, so the client logic (optimistic rollback, abort races, dirty-form guards, keyboard handling) is checked only by hand in the browser.
- Interview angle: "How do you test React components?", "What do you test in a hook?", "Why not test implementation details?"

## Scope

1. **Vitest projects** in `vitest.config.mts`:
   - `unit`: the current setup (`environment: "node"`, `src/**/*.test.ts`, `scripts/**/*.test.ts`)
   - `dom`: `environment: "jsdom"`, `src/**/*.test.tsx`, a setup file that loads `@testing-library/jest-dom/vitest` and runs `cleanup` after each test
   - Projects split by file extension, so **hook tests with `renderHook` are `.test.tsx`** (dom project) too
   - `npm run test` runs both
   - Add `src/**/*.test.tsx` to `SIZE_IGNORES` in `eslint.config.mjs` (only `*.test.ts` is exempt today)
2. **Dev dependencies**: `@testing-library/react`, `@testing-library/user-event`, `@testing-library/jest-dom`, `jsdom` (pin versions; check each against the installed React 19 and Vitest 5)
3. **React Compiler in tests**: it does not run unless it is wired into Vitest (`@vitejs/plugin-react` with `babel-plugin-react-compiler`). Decide in the plan whether tests run with it (closer to production) or without; record the choice in `coding-standards.md`
4. **First tests** (each pins a real rule; colocated as `[name].test.tsx`):
   - `use-item-favorites`: optimistic star, then rollback and error toast when the action fails
   - `use-search-index`: an older response arriving after a newer request does not overwrite it (abort/race)
   - `use-unsaved-changes` or `useDirtyCloseGuard`: closing a dirty form asks first
   - `SortSelect` (`app/(app)/_components/SortSelect.tsx`): choosing a sort calls `onChange` with that sort and shows its label (the URL test belongs to feature 7)
   - one form (`SignInForm`): shows the field error from the action result and keeps the input
   - the item drawer (`items/components/ItemDrawerProvider.tsx`): loading, error and ready states, and an older request cancelled when another item is opened (named in `context/todo.md` "Tests" as the first candidate)
5. **Testing rules** in `context/coding-standards.md` "Testing": query by role and label, `userEvent` over `fireEvent`, mock at the boundary (Server Actions, `next/navigation`, `fetch`), no snapshot tests of markup, async Server Components are not unit-tested (E2E, feature 5)

## Non-goals

Storybook (feature 14), E2E (features 5 and 15), visual tests.

## Acceptance criteria

- `npm run test` runs both projects and is green in CI
- At least the five tests above exist and each fails when its rule is broken (check by breaking it once, then revert)
- The testing section of `coding-standards.md` describes the `dom` project and the rules
