# 10. Import and export

## Why

- Export is sold on the pricing page as a Pro feature ("Export (JSON / ZIP)") and listed in `project-overview.md`, but it does not exist. A promise without a feature is the first thing a reviewer notices.
- Export also serves the GDPR right of access and data portability (Art. 15, 20), which the privacy notice (feature 2) refers to.
- `import-export` is already planned as a rank-7 module in `context/architecture-rules.md`.
- Interview angle: "How do you export a large amount of data without running out of memory?", "How do you validate an import file safely?"

## Scope

### Export (Pro)

1. `GET /api/export` Route Handler (`src/app/api/export/route.ts`, thin: session, entitlements, one service call, headers). The service in `features/import-export/services/export.ts` composes public export reads of `items` and `collections` (no foreign Prisma reads). File metadata with signed links comes from a **public** `items/services/export.ts`, because object keys are read only inside `items/_internal` and another feature may not import it. `items/queries.ts` and `collections/queries.ts` are near the 250-line limit, so new export reads may need their own file
2. **Format: JSON**, versioned (`{ "version": 1, "exportedAt", "items": [...], "collections": [...] }`), streamed with a `ReadableStream` in pages so memory stays flat; `Content-Disposition: attachment; filename="devstash-export-<date>.json"`
3. **Files and images are not packed into the export.** The rule "never proxy file bytes through a Server Action or a route handler" stays: file items carry their metadata and a short-lived presigned download link (expiry stated in the file). The ZIP variant is dropped from the pricing text, or added later with its own ADR
4. Rate limit (one export per minute) with `lib/rate-limit.ts`
5. A `DataSection` on the settings page (name from `docs/modules.md`) with a download button (pending state per the UI/UX rules)

### Import (Pro)

6. **No file upload to the server.** A request body over Vercel's 4.5 MB limit fails (ADR 0004), Server Actions accept 1 MB by default, and file bytes are never proxied. The browser reads the chosen JSON file (size limit, e.g. 5 MB), validates it with the shared Zod schema of the versioned format, rejects unknown versions with a clear message, then sends the records **in batches** (each well under 1 MB) to a Server Action. ADR (cross-file decision 5): "an import is data input in batches, not a file upload"
7. Each record is created through the existing services (`createUserItem`, `createUserCollection`: limits, validation and the advisory lock stay in one place), **one service call per record**. These services open their own transaction, so a batch is not atomic; the result records partial failures. Duplicates by title + type are skipped and counted. (Alternative for the plan review: batch-create services in `items` and `collections`)
8. Result summary: created, skipped, failed (with reasons); re-running the import is safe because of the duplicate check
9. File items in an import come in as links only (no re-upload)

## Non-goals

ZIP archives, importing from other tools, scheduled exports, export for the Free plan.

## Acceptance criteria

- A Pro user downloads a JSON that contains all their items and collections and nothing of other users; a Free user gets the upgrade message
- Export of 2000 items finishes without loading them all into memory at once
- Importing the user's own export into an empty account recreates items, tags and collections; importing it twice creates no duplicates
- A malformed or oversized file is rejected with a readable error, nothing is written

## Tests

Unit: export serializer and import schema (versions, limits). Service tests with mocks for skip/duplicate logic. Integration (feature 4): export contains only the caller's data. E2E later (feature 15): export → import round trip.
