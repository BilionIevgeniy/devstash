# Modules

The catalogue of DevStash's modules: what each one owns, what it uses and what the rest of the code may import from it. It does not repeat the ranks. The numbers live in `FEATURE_RANKS` in `eslint.config.mjs` and in the table "Ranks" in [context/architecture-rules.md](../context/architecture-rules.md), and a module may use any module of a lower rank. The rules for adding a module are in [architecture.md](architecture.md).

A module gets its section here in the commit with its first real code, together with its `FEATURE_RANKS` row. The sections of planned modules are written from the specs and are not built. A test that compares this list with `FEATURE_RANKS` is planned, for existing modules only.

## Who owns which model

| Model | Owner | Note |
| ----- | ----- | ---- |
| User, Account, Session, VerificationToken | `auth` | |
| ItemType | `item-types` | |
| Item, Tag, ItemTag, ItemCollection | `items` | `Tag` becomes its own module only when a second feature needs it; the link to collections is written with the item ([ADR 0008](adr/0008-items-own-the-collection-link.md)) |
| Collection | `collections` | |
| Subscription | `billing` | `isPro` is derived from the subscription status; no row means the Free plan |
| UserPreference | `editor` | One row per user, typed columns, an absent row means defaults, created by upsert |

A module writes only the models it owns and reads only its own models. A relation `select` of scalar columns through its own relation is fine (`items` selects the type name, icon and color through `Item.type`, and the id and name of each collection through `Item.collections`). Everything else goes through the owner's queries or services.

## Existing modules

### auth

- **Owns:** the identity and the session: sign-in, registration, email verification, password reset, change password; for deleting an account, the proof check and the deletion of its rows (the flow itself is `account`'s)
- **Uses today:** `lib` only
- **Entry points used from outside:**
  - `nextauth/session` (`getSessionUser` for pages and actions, which redirects a signed-out caller; `getSignedInUserId` for routes answered with fetch, which returns null instead), `nextauth/auth` (route handlers, `signIn`, `signOut`), `nextauth/auth.config` (used by `proxy.ts`)
  - `actions/sign-in`, `queries`, `schemas`, `services/registration`, `services/account`, and the `domain/` files for tokens, rate limits, reset links and callback paths, all called by pages and routes
  - `services/account` for `account` only: `verifyAccountDeletion` returns a `VerifiedDeletion` that only it can build, and `deleteVerifiedUserRows` takes nothing else, so the rows cannot be deleted without the proof check
  - `components/`: `AuthCard`, the forms (`SignInForm`, `RegisterForm`, `ForgotPasswordForm`, `ResetPasswordForm`, `ConfirmEmailForm`, `ChangePasswordForm`; each a `<form action>` with `useActionState`, see [architecture.md](architecture.md)), `ResendVerificationButton`, `GitHubSignInButton`, `UserAvatar`; `hooks/use-has-session` (the homepage header: a static page learns of the session after mount, for display only)
- **Private:** the actions of its own forms, emails, token and password helpers, error classes, messages, the GitHub grant service, `nextauth/foreign-sign-in` (refuses a GitHub sign-in that resolves to another user while a session cookie exists), `fetch-has-session` (the browser side of `GET /api/auth/session`), `fetch-register` (the browser side of `POST /api/auth/register`, called by the action of `RegisterForm`), `_internal/domain/form-values` (`formValues`, `emptyFormValues`: the text of a submitted form's fields, and the empty start, for the forms; their state is `FormActionState` in `types`), the reads that return a secret (`_internal/queries`, [ADR 0009](adr/0009-read-write-split-enforced-by-lint.md))

### billing

- **Owns:** `Subscription`; the entitlements (limits, Pro) as `domain/limits.ts` plus `queries.ts` `getEntitlements`, read through `cache()` and never from the JWT or the session ([ADR 0011](adr/0011-past-due-grace-and-no-event-table.md)); checkout and portal sessions and the return from Checkout (`services/checkout`, `actions/checkout`); the sync with Stripe (`_internal/services/subscription-sync`, behind the thin route `app/api/webhooks/stripe/route.ts` and `services/webhook`); the billing section of the settings page and the content of `/upgrade`, each with the demo payment hint (`components/TestModeHint`) a Free user sees while Stripe runs on a test key, which the homepage shows under its pricing table too; the pricing table, shared by `/upgrade` and the homepage; stopping the billing of a deleted account
- **Uses today:** `auth` (`getSessionUser` in the actions)
- **Entry points used from outside:** `queries` (`getEntitlements`, `getBillingOverview`), `domain/limits` (`entitlementsFor`, `Entitlements`, the Free limits and Pro prices), `domain/upgrade` (`UPGRADE_PATH`: where a Free user goes for anything the plan does not give), `components/TestModeHint` (the demo payment hint: `/upgrade`, the billing section and, passed in by the homepage, the pricing table; shown only while `isStripeTestMode()`), `components/ProBadge` (the sidebar's file and image types, the same types in the create dialog), `components/PlanBadge` (the user's plan, beside the sidebar's logo and in the billing section), `components/ProUpgradePanel` (the content of `/upgrade`: the pricing table with only what Pro gives today, and one Checkout button for the period of the switch), `components/PricingGrid`, `PricingCard`, `PricingCardButton` and `BillingToggle` (the pricing table of the homepage and `/upgrade`; the grid goes by the width of its container, since `/upgrade` sits beside the sidebar), `components/BillingSection` (the settings page, through `BillingPanel`), `services/webhook` (`handleStripeEvent`, for the route), `services/customer` (`deleteBillingCustomer`, for `account`)
- **Inside the feature only, so far:** `domain/subscription` (`subscriptionWrite`, `stripeIdOf`), `services/checkout`, `actions/checkout`
- **Private:** `getStripeCustomerId` (`_internal/queries`); `_internal/services/subscription-sync` (`syncSubscription`: lock, read from Stripe, write, [ADR 0012](adr/0012-webhook-writes-scoped-by-customer.md)); `BillingActions`, `UsageSummary`; `hooks/use-billing-redirect`, `hooks/use-checkout-return`
- **Today:** created by the file upload spec for the Pro check. Its first migration created `Subscription`; the old `isPro`, `stripeCustomerId` and `stripeSubscriptionId` on `User` stay, read by nothing, until the contract migration in `context/todo.md` drops them. In development the demo user is on the Free plan, one short of both limits: `npm run db:reset-demo` and then `npm run db:seed` bring it back to that start. The seed also creates `demo-pro@devstash.io` with the same content and an active subscription with no customer, on the development database only (`isDevDatabase` in `scripts/require-dev-database.ts`), so the UI can be checked on both plans. On production it keeps the active subscription of migration `demo_user_pro`, with no customer, so the billing section shows it only the badge. `domain/limits` holds the Free limits, enforced by `items` and `collections` in their create services, and the Pro prices, which the homepage pricing and the billing section show

### files

- **Owns:** no model; the objects in R2 under `users/<userId>/`: the file rules (kinds, sizes, the extension → Content-Type map, the extension → icon kind; the browser's `File.type` is never used), the key scheme, presigned upload, the confirm step after the PUT, signed download URLs, deleting and purging objects; `lib/r2.ts` is the vendor client ([ADR 0004](adr/0004-direct-upload-to-r2.md))
- **Uses today:** `billing` (`getEntitlements` in the presign service), `auth` (`getSessionUser` in the action, `tooManyAttemptsParams` from `domain/rate-limits` for the presign limit)
- **Entry points used from outside:** `components/FileUpload` (drop zone, the browser's PUT with progress, aborted on unmount); `components/FileTypeIcon` (the icon of a file by its extension: PDF, text, code, spreadsheet or plain); `services/objects` (`confirmUpload`, `deleteUserObject`, `purgeUserObjects`, `signFileUrls`); `domain/file-rules` (`FileKind`, `formatFileSize`, `fileIconKind`); `types` (`UploadedFile`, `FileUrls`)
- **Inside the feature only, so far:** `actions/upload` (`requestUpload`), `services/presign-upload`, `schemas`
- **Private:** the parts of `FileUpload`: `hooks/use-file-upload` (the upload state, the attempt counter and the abort on unmount), `put-file` (the browser's PUT to R2 with progress, silent on abort), `UploadProgress` (the uploading or finished row) and `DropZone` (the drop area with its hidden file input)
- **Download URLs:** signed at the start of a one-hour window and valid for two, so they repeat across renders (the browser caches images) and stay valid for at least an hour after any render. The caller checks that the key belongs to the user before it asks for them
- **Upgrade path, not built:** a `FileDeletion` outbox processed by a cron route, if deletions start to fail in practice

## Applying the rules to what exists

The rule "a new file starts in `_internal/`" applies to new files. Files that are already public stay where they are, even where nothing outside the module imports them today (`ItemCard` in `items`). Move one only when you touch it for another reason.
